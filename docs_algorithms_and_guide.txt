────────────────────────────────────────────────────────────────────────────────
1. SIMULATION ENGINE
────────────────────────────────────────────────────────────────────────────────

The simulator is a discrete-event, object-centric process simulator driven by
declarative constraints rather than explicit control-flow. It operates in two
modes: standard (step-based) and DES (Discrete Event Simulation with resource
contention and parallel activities).

Standard mode — one activity fires per step
  Step loop (simulator.py → run()):
  1. CANDIDATE GENERATION (candidategeneration.py → build_candidate_for_activity)
     For each defined activity, attempt to build a Candidate by:
     a. Finding active objects of each required type from state._active_by_type
     b. Applying attribute guards (binding.guard): objects not satisfying the
        guard are filtered out before selection
     c. Using _find_objects_preferring_linked: prefer objects already linked to
        other participants (O2O graph preference), fall back to unlinked
     d. Checking semantics (check_all_constraints + check_o2o_rules):
        - check_all_constraints uses _constraints_by_activity index (O(1) lookup)
          to only test constraints involving this activity's name
        - Each constraint checker reads state._events_by_act_obj[(act,oid)] for
          O(1) history lookups per object
        - check_o2o_rules verifies link cardinality caps are not exceeded
     e. Enforcing max_consecutive / max_consecutive_per_object via O(1) streak
        caches (state._global_streak, state._object_streak)
     Result: a list of valid Candidate objects (activity_name + participating
     object IDs + object types to create)

  2. SELECTION (selection.py → select_candidate)
     Weighted random choice from the candidate pool using the transition
     probability matrix (prob_matrix). Each candidate's activity is looked up in
     the matrix for the previously fired activity; the resulting probabilities
     weight the random draw. If no matrix entry exists, uniform random is used.

  3. APPLY (simulator.py → _apply_candidate)
     a. Create new objects of types listed in object_types_to_create, initialising
        attributes from attribute_defaults
     b. Apply O2O links via apply_conservative_link_policy: links are written
        between participating and created objects, respecting max_links caps
     c. Record ExecutedEvent and update all indexes
        (events_by_activity, events_by_object, events_by_act_obj,
         last_activity_per_object, global/object streak caches)
     d. Deactivate objects whose type has deactivates=True on this binding
     e. Apply attribute_updates from binding specs (set / increment / decrement)
     f. Update response obligations (for response constraint tracking)

  4. STOP when step_count >= max_steps or candidate pool is empty

DES mode — multiple activities in-flight simultaneously (run_des())
  Activated when resource_types is non-empty AND activity_durations exist.
  Key differences:
  - Resources are pre-populated from resource_pool_sizes (default 1 per type).
    They are never created by activities — always from the pool.
  - _generate_candidates_des expands one candidate per active primary object
    (capped at 32 per activity to bound cost), not one per activity globally.
  - Each started activity goes into a min-heap (heapq) sorted by complete_at.
  - Clock advances to the next completion timestamp.
  - Resource objects are locked (busy_until) for the activity duration and
    released on completion — enabling queueing (WaitingCandidate list).
  - Attribute updates fire at _des_complete_activity (on completion), not start.


CONSTRAINT SEMANTICS (semantics.py)
Each constraint is checked per-object (for "each" scope) using O(1) indexes:

  precedence(A → B) each T nmin=N :
    B is blocked for object o of type T unless A has fired >= N times on o.
    Uses: count of events in _events_by_act_obj[(A, o)]

  response(A → B) each T nmin=N nmax=M :
    Each A completion creates a requirement for N later matching B completions.
    Eligible B candidates are injected while the requirement remains pending.
    Each/All/Any bindings must match within the same target event. Other semantic
    checks still apply. The existing nmax cap counts completed and running B
    instances; it remains a history-wide cap rather than a per-activation window.

  chain_precedence(A → B) each T :
    B is blocked for object o unless the most recent activity on o was A.
    Uses: _last_activity_per_object[o]

  chain_response(A → B) each T :
    Once A fires on o, every other activity is blocked on o until B fires.
    The constraint "arms" o; only B can disarm it.
    Uses: _last_activity_per_object[o]

  not_coexistence(A ↔ B) each T :
    Once either A or B fires on o, the other is permanently blocked for o.
    Uses: _events_by_act_obj[(A|B, o)] non-empty check

  Attribute guard (binding.guard):
    Before selecting an object for a binding, filter: only keep objects where
    attributes[guard.attribute] <op> guard.value is True. Objects missing the
    attribute are excluded (fail-absent semantics).

O2O LINK POLICY (simulator.py → apply_conservative_link_policy)
  One shared planner validates relationships at candidate admission and again
  immediately before start. It includes old-old, old-new and new-new pairs,
  but only where an O2O rule covers the types. All applicable upper bounds
  must hold, including bounds on newly created objects; directional rules
  constrain only their source side. Invalid plans are rejected before creation.
  Validated links and objects are committed at start; events and obligations
  remain at completion. No random matching or extra random draw is introduced.
  See SEMANTICS.md section 4 for the policy and thesis alignment notes.

2. PROBABILITY DISCOVERY
────────────────────────────────────────────────────────────────────────────────

Function: discover_transition_matrix_object_centric (probabilitydiscovery.py)
Input: OCEL 2.0 log dict

Algorithm:
  1. For each object instance, extract its activity trace: all events it
     participated in, sorted by timestamp.
  2. For each consecutive pair (A, B) in each trace (where A ≠ B), increment
     transitions[A][B].
  3. Count total_fires[A] = total times activity A appeared in any trace.
     Count end_counts[A] = total traces where A was the last event.
     Count start_counts[A] = total traces where A was the first event.
     Compute pos_sums[A] = sum of normalised positions (i/(n-1)) across traces.
  4. Normalise: P(A→B) = transitions[A][B] / total_fires[A]
                P(A ends) = end_counts[A] / total_fires[A]
     These sum to ≤ 1.0 (the remainder is the probability of ending there).
  5. Derive trace_position[A] = mean normalised position (0=always first, 1=last).

Effect on simulation:
  The prob_matrix is used in selection.py to weight the random candidate draw.
  After activity X fires, the matrix row for X gives probabilities for the next
  activity. Activities not reachable from X in the matrix get equal weight.
  Higher probability → more likely to be chosen next.

What distinguishes this from a global approach:
  A global trace sorts all events by timestamp across all cases, creating
  spurious transitions (e.g. Depart → Collect Goods) because two unrelated
  cases happen to be adjacent in time. The per-object approach only counts
  transitions within a single object's life — Depart never follows itself in
  a Container trace, so that transition vanishes.


────────────────────────────────────────────────────────────────────────────────
3. OC-DECLARE DISCOVERY
────────────────────────────────────────────────────────────────────────────────

Function: discover_ocdeclare_model (OCDeclarediscovery.py)
Input: OCEL 2.0 log dict + configuration thresholds

Algorithm (per object type, per constraint template):
  1. Object bindings: for each (activity, object_type) pair that co-occur in
     any event, record the binding with observed min/max objects per firing.
  2. Lifecycle (creates/deactivates): extract per-object traces, identify which
     activity appears first in >= lifecycle_threshold fraction of instances
     (= creator) and which appears last (= terminator).
  3. Resource classification: compute average events-per-instance per type.
     Types with avg >= resource_threshold (default 50) are classified as
     resources (shared, never deactivated).
  4. Constraint mining for each template:
     For each (A, B, scope_type) triple, scan all traces of scope_type objects
     and compute the fraction satisfying the pattern:
       - precedence(A→B): in every trace containing both, does A precede B?
       - response(A→B): in every trace containing A, does B eventually follow?
       - chain_precedence(A→B): whenever B appears, is A the immediately prior?
       - chain_response(A→B): whenever A appears, is B immediately next?
       - not_coexistence(A↔B): do A and B never both appear in the same trace?
     Emit a constraint if the fraction >= confidence threshold.
  5. O2O rules: for each pair of object types, count links per event firing,
     derive min/max cardinalities.

Effect on simulation:
  Constraints are the primary guards. They restrict which activities can fire
  at each step. Tight constraints (chain_response, chain_precedence) cause
  deadlocks if the process doesn't follow the log's dominant sequence exactly.
  Weak constraints (nmin=0, high noise) allow more variation.


────────────────────────────────────────────────────────────────────────────────
4. LIFECYCLE DISCOVERY (for external OC-Declare files)
────────────────────────────────────────────────────────────────────────────────

Function: derive_provisional_lifecycle_from_list (OCDeclare.py)
Input: raw OC-Declare arc list (external format with from/to/arc_type/label)

Algorithm (arc-direction heuristic):
  For each arc mentioning object type T in its label:
    - EP/DP (precedence-like) arcs:
        "from" activity has INPUT arc for T (T arrives at it)
        "to" activity has OUTPUT arc for T (T is produced by it)
    - EF/DF (response-like) arcs:
        "from" activity has OUTPUT arc for T
        "to" activity has INPUT arc for T
    - Unknown arc types: both endpoints get both INPUT and OUTPUT (neutral)

  Entry activities for T = activities with output arcs but no input arcs for T
    → they introduce T into the process → creates=True
  Exit activities for T = activities with input arcs but no output arcs for T
    → they terminate T → deactivates=True

This is a heuristic. It works well when arc directions correctly reflect whether
an activity is the originator or consumer of an object type, but it cannot
distinguish between "creates a new instance" and "uses an existing one" without
actual OCEL log data. For the best results, run OC-Declare discovery on a real
log instead.

When to use: only for external OC-Declare files that lack lifecycle annotations.
Triggered manually via the "↻ Derive lifecycle" button in the Model Editor
header — never run automatically on model load.


────────────────────────────────────────────────────────────────────────────────
5. TIMING DISCOVERY
────────────────────────────────────────────────────────────────────────────────

Function: compute_ocpa_metrics (OCDeclarediscovery.py)
Input: OCEL 2.0 log dict + one or more anchor activity service times

Algorithm (OCPA framework):
  For each event E with timestamp T_complete:
  1. For each participating object o, find the most recent preceding event in
     o's timeline — call its timestamp T_prev(o).
  2. Earliest Arrival = min(T_prev(o)) across all objects
     Latest Arrival   = max(T_prev(o)) across all objects
  3. Sync Time     = Latest Arrival − Earliest Arrival
                     (how long the activity waited for the slowest object to arrive)
  4. Flow Time     = T_complete − Earliest Arrival (total elapsed from first arrival)
  5. Sojourn Time  = T_complete − Latest Arrival (elapsed after all objects arrived)
  6. Pooling Time  = span of latest arrivals across object types
  7. Lagging Time  = which type's latest arrival is the bottleneck

  Service / Waiting (requires at least one anchor):
    For anchor activities: service time = user-provided mean/std/min/max.
    For all others: service ≈ sojourn (if no anchor) or derived from the
    calibration ratio between anchor's known service and observed sojourn.
    Waiting = Sojourn − Service (floor 0).

Effect on simulation (DES mode only):
  The discovered mean_seconds/std_seconds/dist_type per activity drive
  DistributionTimePolicy: it samples a duration from a lognormal distribution
  (default) with those parameters each time the activity fires. This controls
  when the activity completes and when resources are released.

Why one anchor may not be enough:
  Activities that are the first event for all their objects have sojourn = 0
  (no predecessor). If your anchor is such an activity, the calibration
  ratio = known_service / 0 = undefined. Choose an anchor that is a mid-process
  activity with measurable sojourn (not the first in any object's trace).

PART 2 — HOW TO RESTRICT "OBJECT ACTIVE → CANNOT FIRE AGAIN UNTIL DEACTIVATED"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The simulator does not have a built-in "singleton instance per case" flag, but
the combination of existing mechanisms achieves exactly this:

OPTION A — Deactivate + precedence (recommended for linear processes)
  1. Activities tab: on the terminal activity (e.g. "Complete Order"), check
     deactivates=True on the Order binding.
     → When Complete Order fires, that Order object is marked inactive.
  2. Constraints tab: add
       not_coexistence(StartActivity → StartActivity) each Order
     → Once the start activity fires for an Order, it cannot fire again on the
       same Order object.
  3. Because the Order is deactivated after the terminal, the simulator will
     create a fresh Order object for the next case (via creates=True on the
     start activity's binding), starting a new independent instance.

OPTION B — response nmax=1 (simpler, no deactivation needed)
  Constraints tab: add
    response(StartActivity → StartActivity) each Order nmax=1
  → Caps StartActivity at firing exactly once per Order object.
  This does not prevent other activities from using the same Order object
  indefinitely, but prevents the start activity from re-firing on it.

OPTION C — max_consecutive_per_object (for repetition runs)
  Activities tab: set max_consecutive_per_object = 1 on the activity.
  → The same activity cannot fire twice in a row on the same object.
  This allows the activity to fire again after another activity has intervened,
  so it only prevents direct back-to-back repetition.

OPTION D — Attribute guard + attribute update (most flexible)
  1. Attributes tab: add attribute "phase" with default value "idle" to the
     object type.
  2. Start activity binding: add guard {attribute: "phase", op: "==", value: "idle"}
     and attribute_update {attribute: "phase", op: "set", value: "active"}.
  3. Terminal activity binding: add attribute_update
     {attribute: "phase", op: "set", value: "idle"} (or deactivates=True).
  → Start activity is blocked unless phase == "idle". Once it fires, phase
    becomes "active", blocking re-entry until the terminal resets it.
  This allows multiple different states and conditional re-entry beyond just
  "active/inactive".

STEP 1: PARAMETER DISCOVERY
════════════════════════════════

Event Log File (dropdown)
  Which OCEL 2.0 log to analyse. The log drives ALL discovery below it.
  Impact: every count, probability, timing, and constraint is derived from this.

Run Discovery button
  Triggers /api/discover, which computes:
  - Activity counts (how often each activity fired)
  - Transition probabilities (per-object, not global — see Part 1 §2)
  - Per-object repeat stats (min/mean/max firings per object instance)
  - Consecutive run stats (how long the same activity clusters globally)
  - p95 nmax suggestions for max_consecutive_per_object

Discovered Activities table
  Columns:
    Activity — name. Red highlight = no constraints at all. Amber = no input
               constraints (nothing prevents it firing freely).
    P(end) — probability this activity is the last in an object trace. Red
              (≥70%) means it almost always terminates the trace; use as terminal
              activity with deactivates=True.
    ▶ marker — likely start activity (most frequent first event in traces)
    ◼ marker — likely end activity (high P(end))
    Min/Mean/Max consec — how many consecutive times it appears in a row in the
                          log. Use as calibration for max_consecutive.
    Min/Mean/Max /obj — how many times it fires per object instance.
                        Use as calibration for max_consecutive_per_object.
    p95 nmax button — click to apply the 95th-percentile of per-object
                      repeat counts directly to the Model Editor.

Discovered Objects section
  Shows per object type: instance count in the log and observed attribute names.
  Use this to configure the Attributes tab in the Model Editor.

Transition Flow Chart
  Visualises the probability matrix as a directed graph. Node positions reflect
  mean trace position (left=early, right=late). Edge thickness ∝ probability.
  Double ring = start (green) or end (red) activity.
  Min prob slider: filter out low-probability transitions to reduce clutter.
  Nodes and the canvas are draggable; ↺ Reset restores the computed layout.


════════════════════════════════
OC-DECLARE MODEL DISCOVERY
════════════════════════════════

Event Log File — which OCEL 2.0 log to mine constraints from.
  Should be the same log as Step 1 for consistency.

Lifecycle Threshold (default 0.5)
  An activity is a creator/terminator of a type if it's first/last in at least
  this fraction of that type's object traces.
  High (e.g. 0.9) → conservative, only very dominant lifecycle activities flagged.
  Low (e.g. 0.2) → more activities get creates/deactivates, higher false-positive
                    risk in variant-heavy logs.

Resource Threshold (default 50)
  Types with average events-per-instance >= this are classified as resources.
  High → fewer resources detected. Low → more types become resources.
  Resources are pre-populated, never deactivated, and shared across cases.

Confidence / Support / Noise — per constraint template
  Confidence: minimum fraction of traces that must satisfy the pattern for the
              constraint to be emitted.
  Support: minimum fraction of all traces that must contain at least one of the
           involved activities.
  Noise: fraction of violations tolerated. Effective threshold = Confidence − Noise.
  Higher confidence → fewer but more reliable constraints.
  More constraints → more restrictive simulation → more deadlock risk.

════════════════════════════════
MODEL EDITOR
════════════════════════════════

── Activities tab ──────────────────────────

Activity list
  Each activity shown with its bindings, expandable on click.

max consec (global)
  Cap on how many times this activity can fire in a row globally regardless
  of which object. After N consecutive firings globally, it is blocked until
  another activity fires.

max consec/obj
  Cap on how many times this activity can fire in a row on the same object.
  Another activity touching that object resets the counter.
  The p95 button applies the log-derived suggestion.

Binding row per object type
  Object Type — which type this binding covers.
  Min / Max — min and max objects of this type required per firing.
              Min < 1 is treated as "at least 1 for eligibility" (log-derived
              min is a batch-size statistic, not a hard requirement).
  Creates — when checked, this activity may instantiate new objects of this type.
             If the type is a resource, this is always off (resources come from pool).
  Deactivates — when checked, participating objects of this type are marked
                inactive after the activity fires (removed from the candidate pool).
  [guard] — attribute guard: only objects satisfying the condition are eligible.
             Format: attribute_name  operator  value
             Operators: == != > < >= <=
             Objects missing the named attribute are excluded (fail-absent).
  [effects] — attribute updates applied when the activity fires:
               set: obj.attributes[attr] = value
               increment: obj.attributes[attr] += by
               decrement: obj.attributes[attr] -= by
  R badge — object type is a resource; creates is disabled.

── Constraints tab ──────────────────────────

Constraint types:
  precedence(A → B) each T nmin=N
    B is blocked for object o of type T until A has fired >= N times on o.
    nmin=1 (default): B requires A to have happened at least once.
    nmax=N: also caps how many times A may precede B (unusual, use carefully).

  response(A → B) each T nmin=N nmax=M
    Each A creates an independent requirement for N later matching B events.
    The simulator offers feasible response candidates until the count is met;
    nmin=0 creates no positive requirement. The history-wide nmax cap also counts
    running instances. Incompatible models and bounded runs can leave requirements
    unfinished; see SEMANTICS.md for the scope and ordering conventions.

  chain_precedence(A → B) each T
    B requires A as its immediately preceding event on object o. No other event
    on o may intervene. Very strict — causes deadlocks if the process can branch.

  chain_response(A → B) each T
    Once A fires on o, only B may fire next on o. Arms the object; anything
    else touching o is blocked until B fires. Very strict.

  not_coexistence(A ↔ B) each T
    Once either A or B fires on o, the other is permanently blocked for o.
    Use for mutually exclusive paths (e.g. approve / reject).

  not_precedence(A → B) each T
    B is blocked for o if A has ever fired on o. A prevents B permanently.

Scope kinds:
  each — constraint evaluated independently per object instance (recommended)
  any  — constraint applies if any object satisfies / violates it
  all  — constraint applies to all objects in the event simultaneously

nmin / nmax on precedence:
  nmin=1 → standard "A must have happened before B"
  nmin=0 → soft (B can fire even without A; used when A is optional)
  nmax=N → additional upper bound on how many A-occurrences precede B

── O2O Rules tab ──────────────────────────

Object-to-object link rules define which types can be linked and how many.
  Min links — lifetime partner-count target, audited after the run.
              Below-minimum active and inactive objects are reported separately;
              this is not a creation-time blocker or OC-Declare violation count.
  Max links — hard cap. Once an object reaches max_links connections of the
              other type, it is excluded from candidates involving that link.
              This prevents cross-case contamination (e.g. items ↔ orders max=1).
  Bidirectional — apply the same cardinality bounds to both endpoints.
                  Otherwise the bound applies to source objects only.

When max_links is exceeded: check_o2o_rules returns False → activity blocked for
that object combination. Adjust max_links if the simulation gets stuck.

── Timing tab ──────────────────────────

Per-activity duration distributions used in DES mode.
  dist_type: lognormal (default, always positive, right-skewed), normal,
             exponential, or fixed.
  mean_seconds: mean service time in seconds.
  std_seconds: standard deviation (ignored for exponential and fixed).
  min_seconds: floor on sampled values.
  max_seconds: ceiling on sampled values (null = uncapped).

These values are pre-filled when you run Timing Discovery. Override them
manually if the log-derived values are unrealistic.

Reference metrics (sojourn, sync, flow, pooling, lagging) are shown for
information only and do not directly affect sampling.

── Transition Probabilities tab ──────────────────────────

Shows the probability matrix as an editable grid.
  Row = source activity, Column = target activity.
  Each cell is the probability of transitioning to that target after the source.
  Row totals should sum to ≤ 1.0 (remainder = probability of stopping).
  Red total = row sums to > 1.0 (invalid — reduce some values).

Changing probabilities directly affects the simulation's activity selection
without needing to re-run discovery.

── Attributes tab ──────────────────────────

Defines attribute names and types per object type.
  These are the initial attribute values assigned to every newly created object.
  Used together with binding guards and effects for state-based simulation.
  Types: string, float, integer, boolean.

── Resources tab ──────────────────────────

Marks which object types are resources (shared, always-active pools).
  Pool size: how many instances are pre-populated at simulation start.
  Resources are never created by activities and never deactivated.
  DES mode: resources are locked for the duration of an activity and released
            on completion, enabling queueing.

Warning boxes (right side of Model Editor):
  ⚠ Discovered time bounds — activities where min or max is 0 / unbounded.
    Review in Timing tab.
  ⚠ No input constraints — activities with no constraint where they are the
    target. Nothing prevents them from firing freely.
    Red = no constraints at all (no input AND no output constraints).
    Amber = no input constraints but has outgoing constraints.
  ℹ Object Lifecycle — lists resource types and never-deactivated types.
    Never-deactivated types accumulate instances indefinitely during long runs.


════════════════════════════════
TIMING DISCOVERY (after Model Editor)
════════════════════════════════

Mode: Single anchor — provide one activity's known real-world service time.
  All other activities are calibrated relative to this anchor using OCPA metrics.
  Requirements: the anchor must NOT be the first activity in all its object traces
  (first-events have sojourn=0 → calibration undefined). Choose a mid-process
  activity with a known cycle time.

Mode: Multiple anchors — provide several activities with known times.
  Enables more accurate waiting time estimation. Each anchor independently
  calibrates the activities it shares objects with.

Anchor parameters:
  Mean (seconds): expected service time for this activity.
  Std (seconds): standard deviation. Leave 0 for deterministic.
  Min / Max (seconds): clamp the sampled duration. Leave blank for uncapped.

After discovery: results are merged into the Timing tab of the Model Editor.
  Existing user-edited entries are not overwritten.
  Re-running discovery with the same event log will re-derive the metrics.


════════════════════════════════
STEP 3: SIMULATION CONFIGURATION
════════════════════════════════

Start Activities
  Which activities can initiate new object instances at the beginning.
  Marked with ▶ if confirmed by log. At least one must be selected.
  Multiple start activities run concurrently from step 0.
  Impact: defines which object types exist from the start. Activities requiring
  objects that don't exist yet cannot fire.

Max Steps
  Total number of activity firings to simulate.
  Does not correspond to real time — one step = one activity fires.
  In DES mode, the clock advances independently of step count.
  Impact: more steps = more cases / objects created. Runtime scales with model
  complexity (number of constraints × number of active objects per step).
  For simple models: 35,000 steps complete in < 1s. For container_logistics
  with many concurrent objects: ~5ms/step.

Seed
  Random seed for reproducible results. Same seed + same model = same output.
  Change the seed to see different realisations of the same process.

Constraint Health Check (🩺 button)
  Runs 20 simulation steps with constraint instrumentation to identify:
  - Dependency cycles (A requires B, B requires A) → permanent deadlock
  - Permanently blocked activities (never reached the candidate pool)
  - Top blocking constraints (most frequent rejections)
  - Weak precedences (constraint rarely co-occurs in the log — may be alternative
    paths, not sequential requirements)
  Run this before a full simulation to diagnose constraint issues.

SIMULATION OUTPUT
════════════════════════════════

Object Type Breakdown
  Simulated column: how many instances of each type were created.
  In Log column: how many instances exist in the real log (from Step 1 discovery).
  Ratio: Simulated ÷ Log.
    Green (0.5–1.5×): proportional to the real process.
    Amber (>1.5×): simulation created significantly more than reality.
      → Possible causes: too many max_consecutive firings on a creating activity,
        no deactivates on the terminal activity, missing O2O max_links cap.
    Blue (<0.5×): simulation created far fewer.
      → Possible causes: constraints too tight, start activity blocked early.

Activity Distribution
  Bar chart and log of which activities fired and how often.
  Coverage warning: activity types that never fired during the run — these are

Flow Chart
  Object-centric process flow based on the generated event log.
  Shows the actual sequence of events, coloured by object type.

Object Tracer
  Tree view of object-to-object links created during simulation.

Timing Metrics table (if DES mode ran)
  mean_service_s: average time the activity took per firing.
  resource_wait_s: average time spent waiting for a resource to become free.
  High resource_wait → the resource pool is too small for the workload.


════════════════════════════════
CONSTRAINT HEALTH REPORT
════════════════════════════════

Errors (red):
  Dependency cycles — the constraint graph has a loop (A requires B, B requires A
  on the same object type). The simulation will deadlock immediately or after a
  few steps. Remove one edge of the cycle (usually the chain_precedence or the
  precedence with the smaller nmin).

  Permanently blocked activities — never appeared in the candidate pool during
  the 20-step diagnostic run. The top blocking constraint is shown.
  Common causes:
    - Missing creates=True on the binding for the required object type
    - Required object type never gets created by the start activity
    - chain_precedence/chain_response with a predecessor that never fires
    - O2O max_links already saturated from a previous session

Warnings (amber):
  Chain constraints with high rejection counts — these are the most likely
  source of deadlocks in longer runs. chain_response and chain_precedence are
  strict: any activity that touches the scope object before the required one
  fires will permanently block it.
  Fix: downgrade to response / precedence (same requirement, but not immediate).

  Weak precedences — precedence(A→B) where only a small fraction of real traces
  contain both A and B. This suggests A and B are on alternative paths, not
  sequential requirements. The constraint will block the dominant path.
  Fix: remove the constraint or set nmin=0.
